# Choreganizer

A shared chore log for two people: who did which chore, in which room, when. One Nuxt 4 + TypeScript app (Nitro server routes in `server/`, client in `app/`), Postgres via Drizzle, Better Auth, Zod, Nuxt UI, deployed on Vercel. No code yet: [[M0 Skeleton]] sets it up.

## Read first
All planning lives in the Obsidian vault `vault/` (start at `vault/Home.md`). A wikilink `[[Note]]` points to `vault/**/Note.md`.
- `vault/Project/`: scope, data model (schema, server-enforced rules, feed query), API, screens, implementation details (pages, permissions, auth, invites, validation, archiving, ops), stack, open questions.
- `vault/Decisions/`: one note per decision (`status: open | recommended | decided`).
- `vault/Roadmap/Roadmap.md` and `vault/Roadmap/Milestones/M0…M4`: MVP scope and milestone order. Check which milestone has `status: in-progress` before starting work.
- `vault/Plans/`: tech preps and implementation plans, one folder per project (`Plans.base` lists every step and its status). Git-ignored, local only.

`Chore Tracker — Project Plan.md` is the original plan the vault was built from; the vault is newer and wins.

When the plan changes, update the vault notes (keep the YAML properties and `[[wikilinks]]`, tick `- [ ]` tasks in milestone notes, add new decisions with the shape of `vault/Templates/Decision.md`).

## Feature workflow
This repo uses the Obsidian versions of the workflow skills. They replace the Notion and `~/dev/leexi-ai/plans` flow from the global CLAUDE.md here:
1. Milestone note → `obsidian-tech-prep` → `vault/Plans/<Project>/<Project> tech prep.md`, validated in the vault
2. `obsidian-implementation-plan` → `<Project> master.md` + `Steps/<Project> step N.md` in the same folder
3. `obsidian-prepare-step` → step detailed and its open questions settled; no code in that session
4. `obsidian-implement-step`, in a fresh session in auto mode (it holds its plan for approval in plan mode only when the step is stale or risky; start in plan mode to force it) → one branch + draft PR per step, stacked with gh stack
5. `obsidian-step-done` → reconcile the plan with the branch before the PR leaves draft

Conventions for those notes (properties, links, branches, vault commits) are in `.claude/skills/obsidian-tech-prep/references/vault-conventions.md`.

When local `master` is ahead of `origin/master` (usually the vault commit `obsidian-step-done` leaves), cut a step branch based on `master` from local `master`, not `origin/master`, without asking: those commits ship in that step's PR. The step being implemented is the one whose `branch:` property is the current branch; its `## Deviations` section takes the global deviation-log lines.

## Product rules
- Logging a chore takes **two taps on a phone**. Anything on the logging path that adds a tap, a required field or a wait is a bug. Defaults do the work: done by me, done now.
- Authorization lives on the server: every route calls `requireMembership` (or loads the row and checks its `apartment_id`). Never trust an `apartmentId` from the client; `done_by` is always the session user.
- The rules the database can't enforce (`vault/Project/Data model.md` § Rules the server must enforce) are checked in the route that writes.
- Archive, never delete: tasks, rooms and apartments get `archived_at`; history must never break. Logs are the one thing that can be deleted.

## Conventions
- One file per route under `server/api/`, matching `vault/Project/API.md`; shared rules in `server/utils/` (auto-imported).
- Zod schemas shared between a form and its route; limits from `vault/Project/Implementation details.md` § Validation.
- Migrations are generated by Drizzle Kit from the schema and committed. Never edit one that's already applied.
- Timestamps in UTC; "today" and day grouping use the apartment's timezone.
- User-facing text is in French (`fr-BE` for dates).
- Tests where they pay off: the log-creation rules, `requireMembership`, and one Playwright happy path. CI runs lint, typecheck and tests on every PR.
- Branches are `<type>/<slug>` off `master`. PR titles and descriptions follow the `write-pr-description` skill: a quick summary, a manual test pass, and the vault design a PR implements.
