# Chore Tracker — Project Plan

Oct 27, 2026 · @Léo

## Scope

The MVP is a shared log: two people record "who did which chore, in which room, when", and read that history back. Everything else (reminders, due dates, stats) is built on top of those logs later.

The one product rule that decides whether this app gets used: **logging a chore must take two taps on a phone, right after doing it.** If it takes longer, you will stop logging within two weeks and the data becomes useless.

**In the MVP**

- Apartments: create, rename, archive; each has a list of rooms
- Members: invite the other person to an apartment; a person can belong to several apartments (home, holiday rental)
- Tasks: name, frequency (daily, weekly, every N days…), and where it applies (anywhere, or a chosen set of rooms)
- Logs: "I did X in room Y", timestamped now by default, editable afterwards
- Feed: "Alice did *Nettoyer les vitres* in the kitchen · yesterday 19:40", newest first, filterable by person, task, room

**Not in the MVP** (deliberately)

- "What's due / overdue" dashboard: the frequency is stored from day one so this is a pure read feature later
- Notifications, points, fairness stats, task assignment
- Native mobile app: a responsive web app installable as a PWA is enough

## Decisions to settle before coding

These shape the schema, so it's worth agreeing on them with your girlfriend first. My recommendation is in the last column; each one keeps the MVP small without blocking later features.

| Question | Options | Recommendation |
| --- | --- | --- |
| What does "anywhere" mean for a task like *Passer le balai*? | A list of every room, or a flag | An `all_rooms` flag, so a room you add later is included automatically |
| When logging an "anywhere" task, do you pick a room? | No room · one room · several rooms | Optional, several allowed; zero rooms means "the whole flat" |
| Is "weekly" per task or per room? | *Vitres* once a week overall, or once a week in each room | Store frequency on the task; compute "due" per task + room later. Doesn't affect the MVP |
| Rolling or fixed schedule? | "7 days after last done" vs "every Monday" | Rolling interval: it matches how chores actually happen |
| Can you log a chore for the other person? | Only yourself, or anyone | Anyone, but store `done_by` and `logged_by` separately |
| Can you log in the past? | Now only, or any time | Defaults to now, editable ("I did it yesterday") |
| What happens to logs when a task or room is removed? | Hard delete, or archive | Archive only (`archived_at`); history must never break |
| Tasks per apartment or shared templates? | Per apartment, or a global library | Per apartment; add "copy tasks from another apartment" after the MVP |

One more detail: give each apartment a `timezone` (default `Europe/Brussels`). Store every timestamp in UTC, and use the apartment's timezone to decide what "today" or "this week" means.

## Data model

Nine tables. Everything hangs off `apartments`, and every query is scoped by "is the current user a member of this apartment".

&#91;embedded content: table relationships · 9 tables\]

Rooms and tasks meet through `task_rooms`; a log points at one task, a person, and zero or more rooms through `log_rooms`.

| Table | Holds | Notes |
| --- | --- | --- |
| `user` | You and your girlfriend | Better Auth's own table (text `id`, `name`, `email`); `name` is the display name. Its `session`, `account`, `verification` tables come with it |
| `apartments` | A flat, a holiday rental | `archived_at` when you move out, `timezone` |
| `memberships` | Who belongs to which apartment | Many-to-many; `role` owner / member |
| `invites` | Single-use join codes | Expires after 7 days; records who used it |
| `rooms` | Rooms of one apartment | `position` for ordering, `archived_at`; name unique among active rooms |
| `tasks` | Chores of one apartment | Frequency + `all_rooms` flag, `archived_at`; name unique among active tasks |
| `task_rooms` | Which rooms a task applies to | Ignored when `all_rooms` is true |
| `logs` | One completion of a task | `done_by`, `logged_by`, `done_at`, optional note |
| `log_rooms` | Which rooms a log covered | Zero rows = whole apartment |

Postgres schema (stack-agnostic; translate to Drizzle or Prisma later):

```sql
-- Users: Better Auth's "user" table (id text, name, email, ...), generated by
-- its CLI into the same Drizzle schema. Every user FK below is text.

create table apartments (
  id          uuid primary key default gen_random_uuid(),
  name        text not null,
  timezone    text not null default 'Europe/Brussels',
  archived_at timestamptz,
  created_at  timestamptz not null default now()
);

create table memberships (
  apartment_id uuid not null references apartments(id) on delete cascade,
  user_id      text not null references "user"(id) on delete cascade,
  role         text not null default 'member' check (role in ('owner','member')),
  joined_at    timestamptz not null default now(),
  primary key (apartment_id, user_id)
);

create table invites (
  code         text primary key,              -- nanoid(12), URL-safe
  apartment_id uuid not null references apartments(id) on delete cascade,
  created_by   text not null references "user"(id),
  expires_at   timestamptz not null,
  used_at      timestamptz,
  used_by      text references "user"(id)
);

create table rooms (
  id           uuid primary key default gen_random_uuid(),
  apartment_id uuid not null references apartments(id) on delete cascade,
  name         text not null,
  position     int  not null default 0,
  archived_at  timestamptz
);
create unique index rooms_active_name_idx
  on rooms (apartment_id, lower(name)) where archived_at is null;

create table tasks (
  id                 uuid primary key default gen_random_uuid(),
  apartment_id       uuid not null references apartments(id) on delete cascade,
  name               text not null,
  description        text,
  all_rooms          boolean not null default false,
  frequency_interval int,      -- e.g. 1, 2, 3
  frequency_unit     text,     -- 'day' | 'week' | 'month'; both null = "as needed"
  archived_at        timestamptz,
  created_at         timestamptz not null default now(),
  check ((frequency_interval is null) = (frequency_unit is null)),
  check (frequency_interval is null or frequency_interval between 1 and 365),
  check (frequency_unit is null or frequency_unit in ('day','week','month'))
);
create unique index tasks_active_name_idx
  on tasks (apartment_id, lower(name)) where archived_at is null;

create table task_rooms (
  task_id uuid not null references tasks(id) on delete cascade,
  room_id uuid not null references rooms(id) on delete cascade,
  primary key (task_id, room_id)
);

create table logs (
  id           uuid primary key default gen_random_uuid(),
  apartment_id uuid not null references apartments(id) on delete cascade,  -- denormalised for fast feeds
  task_id      uuid not null references tasks(id),
  done_by      text not null references "user"(id),
  logged_by    text not null references "user"(id),
  done_at      timestamptz not null default now(),
  note         text check (length(note) <= 500),
  created_at   timestamptz not null default now()
);
create index logs_feed_idx on logs (apartment_id, done_at desc, id desc);

create table log_rooms (
  log_id  uuid not null references logs(id) on delete cascade,
  room_id uuid not null references rooms(id),
  primary key (log_id, room_id)
);
```

**Rules the database can't enforce, so the server must:**

- A task's rooms, a log's task and a log's rooms all belong to the same apartment
- A log's rooms are among the task's eligible rooms (all active rooms if `all_rooms`, else `task_rooms`)
- `done_by` is a member of the apartment
- Archived tasks and rooms can't receive new logs, but still show in the feed

The feed query is then a single join:

```sql
-- $2, $3 = done_at and id of the last row on the previous page (null for page 1)
select l.id, l.done_at, u.name as who, t.name as task,
       coalesce(array_agg(r.name order by r.position) filter (where r.id is not null), '{}') as rooms
from logs l
join "user" u on u.id = l.done_by
join tasks t on t.id = l.task_id
left join log_rooms lr on lr.log_id = l.id
left join rooms r on r.id = lr.room_id
where l.apartment_id = $1
  and ($2::timestamptz is null or (l.done_at, l.id) < ($2, $3))
group by l.id, u.name, t.name
order by l.done_at desc, l.id desc
limit 50;
```

## Stack

Recommended: one TypeScript codebase, one Postgres database, free hosting. It's the shortest path to a deployed app for a CRUD product like this one.

| Layer | Pick | Why |
| --- | --- | --- |
| Framework | Nuxt + TypeScript | Vue front and Nitro server routes in one repo; `server/api` files map 1:1 to the API below |
| Database | Postgres on Neon or Supabase (free tier) | Relational data with real constraints; the schema above runs as-is |
| ORM | Drizzle | Typed queries close to SQL, simple migrations; runs fine inside Nitro |
| Auth | Better Auth, email + password | Has a Nuxt integration; sessions and users tables out of the box |
| Validation | Zod | Same schemas for Nuxt UI forms and `readValidatedBody` on the server |
| UI | Nuxt UI (Tailwind-based) | Mobile-friendly forms, drawers, modals and toasts out of the box |
| Hosting | Vercel or Netlify | Nitro presets for both; push to deploy, preview URLs per branch |
| Mobile | `@vite-pwa/nuxt` | Manifest + service worker for "Add to home screen" |

**Good alternatives, if they fit you better**

- **nuxt-auth-utils** instead of Better Auth: lighter (sealed cookie sessions, password hashing helpers), but you own the users table and sign-up flow.
- **Prisma** instead of Drizzle: more batteries included, heavier client.
- **Supabase as the backend** (`@nuxtjs/supabase`): auth + row-level security, but authorization logic lives in SQL policies, which is harder to debug.
- **Self-hosting**: `nuxi build` outputs a Node server (`.output/server/index.mjs`) that runs on any small VPS or in Docker.

## API

Written as REST routes for clarity; in Nuxt each one is a file under server/api/ (e.g. server/api/apartments/\[id\]/logs.post.ts), called from pages with useFetch or $fetch. All routes require a session.

| Method | Route | Does |
| --- | --- | --- |
| GET | `/apartments` | Apartments I'm a member of (active first) |
| POST | `/apartments` | Create; creator becomes owner |
| PATCH | `/apartments/:id` | Rename, change timezone, archive / unarchive |
| GET | `/apartments/:id/members` | List members |
| POST | `/apartments/:id/invites` | Create a join code (owner only) |
| POST | `/invites/:code/accept` | Join the apartment; marks code used |
| DELETE | `/apartments/:id/members/:userId` | Leave, or remove someone (owner only) |
| GET · POST | `/apartments/:id/rooms` | List, create |
| PATCH | `/rooms/:id` | Rename, reorder, archive |
| GET · POST | `/apartments/:id/tasks` | List (with eligible rooms), create with `roomIds` or `allRooms` |
| PATCH | `/tasks/:id` | Edit name, frequency, rooms; archive |
| POST | `/apartments/:id/logs` | Log `{taskId, roomIds?, doneBy?, doneAt?, note?}` |
| GET | `/apartments/:id/logs` | Feed; filters `userId`, `taskId`, `roomId`, `from`, `to`; cursor on `done_at` |
| PATCH · DELETE | `/logs/:id` | Fix or remove a mistaken log |

**Authorization, in one helper.** Write `requireMembership(event, apartmentId)` once in `server/utils/` (auto-imported) and call it at the top of every handler. For routes keyed by a room, task or log id, load the row first and check membership on its `apartment_id`. Never trust an `apartmentId` from the client without that check.

**Log creation, step by step:** check membership → load the task (active, same apartment) → resolve eligible rooms → reject any `roomId` outside them → check `doneBy` is a member (default: me) → insert `logs` and `log_rooms` in one transaction.

## Screens

Five screens. The home screen is the logging screen, not a dashboard, because logging is the action you do ten times a week.

| Screen | Contents |
| --- | --- |
| Sign in / sign up | Email + password; after sign-up, "create an apartment" or "enter an invite code" |
| Home: log a chore | Apartment switcher at the top; one large button per active task, showing "last done 3 days ago by Alice" |
| Feed | Logs grouped by day: "Alice · Nettoyer les vitres · Cuisine, Salon · 19:40"; filter chips for person, task, room; tap a log to edit or delete |
| Tasks | List + form: name, description, frequency (as needed / every N days, weeks, months), rooms ("Anywhere" toggle or room checkboxes) |
| Apartment settings | Name, timezone, rooms (add, rename, drag to reorder, archive), members, "invite" button that shows a code and share link, archive apartment |

**The quick-log flow**

1. Tap a task on Home.
2. If the task has exactly one eligible room, it's logged immediately.
3. Otherwise a bottom sheet shows room chips plus "Whole flat"; pick one or more, tap **Done**.
4. A toast confirms with **Undo** (deletes the log) and **Edit** (change who, when, add a note).

Defaults do the work: done by me, done now. Changing either is possible but never required.

## Implementation details

These defaults fill the gaps between the schema and the code. Each one can change; none should be decided mid-commit.

**Pages** (Nuxt `pages/`)

| Route | Screen |
| --- | --- |
| `/login`, `/signup` | Auth |
| `/` | Redirects to the last-used apartment (cookie `last_apartment`), or to `/onboarding` if you have none |
| `/onboarding` | Create an apartment or enter an invite code |
| `/join/[code]` | Accept an invite; signed-out visitors go through sign-up, then return here |
| `/a/[apartmentId]` | Home: log a chore |
| `/a/[apartmentId]/feed` | Feed |
| `/a/[apartmentId]/tasks`, `/tasks/new`, `/tasks/[taskId]` | Task list and form |
| `/a/[apartmentId]/settings` | Apartment, rooms, members, invites |

A client route middleware sends signed-out users to `/login?redirect=…`. The real access check stays on the server.

**Permissions**

| Action | Owner | Member |
| --- | --- | --- |
| Rename apartment, change timezone | Yes | Yes |
| Archive / unarchive apartment | Yes | No |
| Create invites, remove members | Yes | No |
| Rooms, tasks, logs: create, edit, archive, delete | Yes | Yes |
| Leave apartment | Yes | Yes |

If the last owner leaves while someone remains, that person is promoted to owner in the same transaction. If nobody remains, the apartment is archived.

**Auth**

- Better Auth with the Drizzle adapter; its CLI generates `user`, `session`, `account`, `verification` into your schema
- `requireUser(event)` in `server/utils/` calls `auth.api.getSession({ headers: event.headers })` and throws 401; `requireMembership` builds on it
- No password reset in the MVP: a small `scripts/reset-password.ts` covers two users. Add Resend and Better Auth's reset flow later if needed

**Invites**

- Code: `nanoid(12)`, shared as a `/join/<code>` link; 12 random characters make guessing impractical, so no rate limiting needed
- Valid for 7 days, single use: setting `used_at`/`used_by` and inserting the membership happen in one transaction
- Already a member → redirect to the apartment; expired or used → clear error page

**Validation** (Zod on the server; the same schemas in Nuxt UI forms)

- Names trimmed, 1–60 characters; a duplicate active name returns 409 with "A room called *Cuisine* already exists"
- Frequency interval 1–365; note ≤ 500 characters
- `done_at` no more than 5 minutes in the future (clock skew); no lower limit

**Archiving**

- Apartments, rooms and tasks can be archived and unarchived
- Archiving a room removes it from new logs and from "all rooms"; its `task_rooms` rows stay, so unarchiving restores the setup
- Archived items still appear in the feed and its filters, greyed out

**Feed**

- 50 logs per page; cursor = `done_at` + `id` of the last row (see the query above)
- Day grouping uses the apartment's timezone via `Intl.DateTimeFormat`
- Refetch when the tab regains focus; no realtime

**Ops**

- Drizzle Kit migrations committed to the repo, run in the deploy step
- Confirm point-in-time restore is enabled on the Neon or Supabase project

## After the MVP

The schema already supports each of these without a migration, except where noted.

- **Due / overdue view:** for each task (and room, for room-specific tasks), last `done_at` + interval vs. today in the apartment's timezone
- **Balance stats:** chores per person per week, optionally weighted by an `effort` column on tasks (needs a migration)
- **Reminders:** a daily cron that sends a push or email digest of overdue tasks
- **Copy apartment:** duplicate rooms and tasks into a new apartment when you move or go on holiday
- **Fixed schedules:** "every Monday" via an RRULE column, if rolling intervals turn out not to fit some chores
